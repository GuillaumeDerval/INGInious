# LTI session and cookieless `?session_id=` mechanism

- **ID**: LTI-03
- **Actors**: LTI user (any page rendered inside the LMS iframe)
- **Routes**: all routes (query parameter `session_id`); session creation on POST /lti/<courseid>/<taskid> and GET|POST /lti1.3/launch…
- **Depends on**: session management (AUTH area), LTI-02, LTI-09
- **Legacy code**: `legacy/inginious/frontend/flask/mongo_sessions.py:35-82`,
  `legacy/inginious/frontend/app.py:81-87,189-193` (`add_lti_session_id`),
  `legacy/inginious/frontend/pages/utils.py:28-31,92-139` (`is_lti_page` checks),
  `legacy/inginious/frontend/models/session.py:12-63`,
  `templates/layout.html:131,137,146,204-212`, `templates/task.html:27,127,152,274,349-353`,

## Use case
INGInious pages are displayed inside an iframe of the LMS, where third-party cookies are
usually blocked. The session is therefore carried in the URL (`?session_id=<token>`) for
the whole LTI navigation, and an LTI session can only use the LTI pages (no navigation
chrome).

## Preconditions
- An LTI session was created by a launch (LTI-02 / LTI-09).

## Main flow
Behaviour of the app (`app/src/lib/server/auth/session.ts`, `request.ts`,
`security/guards.ts`, `lti/common.ts`):
1. **Session creation**: a valid launch (LTI-02 / LTI-09) replaces the session of the
   request by a new session document flagged `is_lti = true`, never loaded from an
   existing cookie or token.
2. **Session token**: the token is `<session id>.<HMAC-SHA256(server secret, id)>`, the
   same format as the session cookie. The `?session_id=` query parameter is only read on
   the LTI paths (`/lti/…` and `/lti1.3/…`); there it takes precedence over the cookie.
   A token that is malformed or wrongly signed is ignored (the cookie session, if any, is
   used); a correctly signed token designating a session not flagged `is_lti` gives a new
   empty session.
3. **Session loading and saving**: the session is loaded by `_id`; an expired document
   (`expiration <= now`) is deleted and replaced by a new session. The sliding expiration
   (`now + timeout`, default 86400 s) is refreshed at most once a minute. LTI sessions
   never get a `Set-Cookie`.
4. **URL propagation**: the LTI pages build their links explicitly with
   `?session_id=<token>`: `redir_url`, login and task URLs, the task form action and the
   rewritten statement assets (LTI-06). The bind link carries a separate short-lived
   bind token as `lti_session_id` (LTI-04).
5. **Page restriction**: outside the LTI paths the `?session_id=` parameter is ignored, so
   an LTI session cannot reach the normal pages; in addition the user guards refuse a
   session flagged `is_lti` outside the LTI paths (403 "This page is not available from
   your LMS."). LTI responses are sent without `X-Frame-Options: DENY` so that the LMS can
   frame them; every other response has it.
6. **Layout in LTI mode**: no top navbar and no sidebar menu; the task page shows the
   student view without deadline row, staff administration box, "Submitting as" box or
   previous/next navigation, and its form posts to the LTI task URL of the session
   (`/lti/task?session_id=…` or `/lti1.3/task?session_id=…`).

Legacy reference (functional): legacy propagated the id through a Flask `url_defaults`
hook (every `url_for` of an LTI request got `session_id=`, or `lti_session_id=` for the
bind pages), saved the session on every request, and its LTI task form always posted to
`/lti/task`, also for LTI 1.3 sessions. Two legacy bugs are not reproduced: the social
sign-in pages looped on themselves in an LTI session, and the uploaded-file download link
of the task page got two `?` in LTI mode.

## Alternative / error flows
- A normal (non-LTI) page requested with `?session_id=<lti token>` ignores the parameter
  and uses the browser cookie session, if any; the LTI session is unaffected.
- Session expired/deleted → a new empty non-LTI session is used; the LTI pages answer 403
  "No LTI data available.".
- `?session_id=` that is malformed or wrongly signed → ignored: the cookie session, if any,
  else a new empty session, is used (never an LTI session).

## UI elements
- LTI layout differences listed in step 6.

## Data
`sessions` collection document:
```
_id: ObjectId (primary key, generated by the frontend at creation)
permanent: bool (required)            is_lti: bool (default false)
loggedin: bool (default false)        auth_storage: {str: any}
expiration: Date (TTL index, expireAfterSeconds 0)
lti: LTIData | null                   code_indentation: "2"|"3"|"4"|"tabs" (default "4")
email, realname, username: str|null   language: str (default "")
token: str|null                       tos_signed: bool
timezone: str (default local tz name)
```
`LTIData` sub-document: `version` ("1.1"|"1.3"), `email`, `username` (LMS user id),
`realname`, `roles: [str]`, `task: [courseid, taskid]`, `redir_url`, `context_title`,
`context_label`, `tool_description`, `tool_name`, `tool_url`; 1.1: `consumer_key`,
`outcome_service_url`, `outcome_result_id`; 1.3: `message_launch_id`,
`platform_instance_id`, `course_secret`. All strings, `None` fields omitted by
mongoengine.

## Permissions & security
- The `?session_id=` token is signed with the server secret (HMAC-SHA256, constant-time
  verification), is only read on the `/lti/…` and `/lti1.3/…` paths, is only accepted for
  sessions flagged `is_lti`, and is never turned into a cookie.
- Session ids alone are not usable without their signature.
- LTI sessions are created only by a valid launch and expire after the session timeout
  (default 24 h) without activity.
- Outside the LTI paths a session flagged `is_lti` is refused by the user guards (403).

## Acceptance tests
- A launch creates a session with `is_lti=true` and no cookie; subsequent links carry
  `session_id`.
- Links of an LTI page (form action, asset links, login/task redirects) contain
  `session_id=<token>`; the bind link contains `lti_session_id=<bind token>`.
- `/mycourses?session_id=<lti token>` does not use the LTI session.
- LTI layout: no navbar/sidebar menu, task form action `/lti[1.3]/task?session_id=…`.
- Expired LTI session → 403 "No LTI data available." on `/lti/login`.
- Test: a non-LTI session id passed as `?session_id=` does not authenticate; an unsigned
  or wrongly signed `?session_id=` does not authenticate.
